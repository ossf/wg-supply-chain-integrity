# Working Group Chair Onboarding

Welcome, and thank you for taking on a chair/lead role. This guide walks through
what the role involves and what to set up in your first few weeks. It is
**non-exhaustive** — for authoritative process details, always defer to the
linked upstream [OpenSSF TAC](https://github.com/ossf/tac) documents.

> This guide is written to be reusable by any OpenSSF Working Group, not just
> this one — it deliberately doesn't repeat this WG's specific links (mailing
> list, Slack, calendar, roster, lifecycle stage). Those live in this repo's
> top-level README and stay current there rather than in a second copy here.

## What the role involves

The TAC's canonical job description is
[WG Lead Roles & Responsibilities](https://github.com/ossf/tac/blob/main/process/wg-lead-R%26Rs.md).
In short, as chair you:

* Facilitate WG meetings — agendas, calls for topics, capturing and following up on action items
* Drive progress on the WG's efforts (specifications, code, or other contributions)
* Provide technical guidance and sponsorship for sub-projects, coordinate with related Projects/SIGs, and arbitrate technical disputes as needed
* Present quarterly WG updates to the TAC and keep the WG's work legible across OpenSSF community channels
* Facilitate WG voting as needed
* Keep the WG on track with its mission, and negotiate any desired changes with the TAC
* Own GitHub repo management — issue/PR backlog, edits/updates — or explicitly delegate it
* Expect a time commitment of roughly 2-3 hours per week

## Know your WG's lifecycle stage

WGs progress through **Sandbox → Incubating → Graduated → Archived**, each with
different obligations owed to the TAC. Read the full requirements in
[TAC's Working Group Lifecycle](https://github.com/ossf/tac/blob/main/process/working-group-lifecycle.md)
before your first quarterly update — it defines what "in good standing" means at
your current stage (meeting cadence and public notes, contributor/org diversity
thresholds, charter/README approval, quarterly reviews, etc.).

To request a lifecycle-stage change, a chair opens a PR against `ossf/tac` using
the appropriate template from
[process/templates](https://github.com/ossf/tac/tree/main/process/templates).

## Access & tooling checklist

Work through this in your first week:

* [ ] Confirm you're listed as a chair/lead in this WG's README
* [ ] Get added to any relevant GitHub team(s) / `CODEOWNERS` entries for this repo
* [ ] Join the WG's mailing list
* [ ] Join the WG's Slack channel(s)
* [ ] Subscribe to the WG's public meeting calendar
* [ ] Get edit access to the WG's meeting notes/agenda doc
* [ ] Introduce yourself in the WG's Slack channel and at the next meeting

This mirrors the pattern in the TAC's own
[member onboarding doc](https://github.com/ossf/tac/blob/main/process/tac-onboarding.md),
which is a useful reference even though it's written for TAC members rather
than WG chairs.

## Communications

Default to public communication whenever possible, even for routine topics —
this keeps the WG legible to the wider OpenSSF community and lowers the barrier
for new contributors. Typical channels:

* WG Slack channel and mailing list, for day-to-day coordination
* Public meeting notes, for anyone who couldn't attend live
* Quarterly updates to the TAC (see [TAC Decision Process](https://github.com/ossf/tac/blob/main/process/TAC-Decision-Process.md) for format/cadence expectations)

## Meetings

* Send an agenda ahead of each meeting; take a call for topics beforehand
* Capture notes and action items during the meeting, and follow up on open items before the next one
* Periodically review whether meeting cadence and format still serve the WG — this is one of the things TAC reviews at lifecycle-stage changes

## Keeping governance docs current

As chair, you're responsible for keeping these accurate — they rot quickly if
no one owns them:

* This WG's Charter
* The WG's roster (README's Governance section)
* This onboarding guide itself, if the role or process changes
* The governance README's status/lifecycle references

## Getting help

* Your WG's **TAC sponsor** — assigned at Sandbox stage, remains a resource through Incubating
* **OpenSSF staff** — reachable via `operations@openssf.org` or the `#openssf-operations` Slack channel
* Other WG chairs — the fastest way to learn what's normal is to ask someone doing the same job elsewhere
